三、移动语义与展示序号的三个关键推论
--------------------------------------------------------------------------------

1. 目标序号表示最终位置。移动分两步完成：先把来源条目从列表中取出
   （ids.pop(int(from_text) - 1)，release_notes.py:514），再把它
   插入目标序号处（ids.insert(int(to_text) - 1, ...)，:515）。
   insert 的下标就是目标序号减一，不做“来源在前则目标减一”的
   修正，因此移动后来源条目恰好位于目标序号（注释
   release_notes.py:502-505 明示；公开约定 README.md:228-231）。
   本流程中 --from 02 --to 03 的结果是：两行文本从第 2 条变为
   第 3 条，原第 3 条（第二条 新增预览）前移为第 2 条。

2. 记录数不等于输出行数。序号按记录计数而非按输出行数计数：
   locate_change 的 COUNT(*) 与 LIMIT/OFFSET 都作用于 changes
   表的行（release_notes.py:372-391，docstring :365-366 明示
   “多行条目只占一个序号”）；一条 content 含内部换行的记录仍是
   一条记录、占一个序号。但输出按文本逐行展开：show 在首行前加
   "- " 后原样写出（release_notes.py:150-153），export-markdown
   同样保留内部换行（release_notes.py:221-227）。因此移动后
   记录数为 3，show 的输出行数却是 6（2 行头部 + 2 条单行记录
   + 1 条两行记录）。这是公开约定（README.md:51、176-177、
   232-233），与源码一致。

3. 新进程仍读到相同顺序。程序无跨进程内存状态：每次调用各自
   sqlite3.connect 并在 finally 关闭（如 release_notes.py:294、
   469-470、520-521）；顺序的唯一来源是持久化在 notes.sqlite
   中的 position 列与各处 ORDER BY position 查询（read_draft
   :130-137；locate_change :387-391；move-change 取 id 列表
   :506-513）。move-change 已把新顺序写回 position
   （release_notes.py:516-519）并随 with conn 事务提交
   （:489），因此结束进程后在新进程中用同一 --db 路径执行
   show / export-markdown / 后续 move-change，看到的顺序完全
   相同（顺序持久化是源码推演；“新进程同路径可再读”的用法在
   README.md:271-274 有公开示例）。

另两点输入层面的推论（公开约定 README.md:232-234、239-240）：

4. 前导零只影响输入写法。validate_change_index 用 lstrip("0")
   归一化（release_notes.py:279），"02" 与 "2" 定位同一记录；
   输出与错误消息中的序号一律为去前导零后的形式，因此本流程
   成功输出是 Moved change: demo-0.2 #2 -> #3 而非 #02 -> #03。

5. 同位置移动成功且顺序不变。来源与目标相同（如 --from 2
   --to 2）时，pop 与 insert 的下标相同，列表不变，UPDATE 把
   原 position 原样写回，仍输出 Moved change: <版本名> #N -> #N
   并返回 0（release_notes.py:514-519、523-524；公开约定
   README.md:231）。

四、move-change 的失败优先级：检查、定位、写入的先后
--------------------------------------------------------------------------------

move-change 按下列先后返回失败，先命中先报（cmd_move_change，
release_notes.py:475-524）：

  第 1 步 输入检查（不触碰数据库）
    release_notes.py:480-483：--from 与 --to 分别经
    validate_change_index（release_notes.py:265-279）判定，再与
    版本名一起检查。以下任一情形均返回 Invalid draft：
      - 未提供 --from 或 --to（None 经 or [] 归一后 len != 1，
        :275-276）；
      - 重复提供任一选项（多于一个，同样 len != 1）；
      - 版本名为空或仅由空白组成（is_blank，release_notes.py:42-44、
        482）；
      - 序号为空白串（"" 不匹配正则，:277-278）；
      - 序号含非 ASCII 数字（正则字符类 [0-9] 只接受 ASCII 数字
        0-9，全角数字等一律不匹配，:277-278）；
      - 序号数值为 0（"0"、"00" 等不满足 0*[1-9][0-9]* 中必须
        出现 1-9 的要求，:277-278）。
    → 失败：Invalid draft。校验整体位于 os.path.exists
      （release_notes.py:291）与 sqlite3.connect
      （release_notes.py:294）之前，即使数据库文件不存在也优先
      返回此结果，本进程不打开、不创建数据库文件（公开约定
      README.md:241-243）。

  第 2 步 打开并确认版本（不写入）
    open_draft_for_update，release_notes.py:282-315：数据库文件
    不存在时直接失败（:291-292），不 connect、不建库；文件存在
    但没有 drafts 表（完全空库或只有无关表）时失败（:299-305），
    不补建表；drafts 中无该版本时失败（:309-314）。
    → 失败：Version not found: <版本名>。两个序号均合法但数据库
      缺失、缺 drafts 表或版本不存在时返回此结果（公开约定
      README.md:244-245）。

  第 3 步 定位来源与目标（不写入）
    locate_change，release_notes.py:365-392：先 COUNT(*) 得条目
    总数（:372-375），序号与总数按十进制位数与字典序比较判定
    越界（:377-385），在界内才执行 LIMIT 1 OFFSET 查询
    （:387-391）。版本存在后先检查来源（release_notes.py:491-495）
    再检查目标（:496-500）。
    → 失败：Change not found: <版本名> #<规范化序号>。来源越界
      报来源序号；来源有效而目标越界报目标序号；两者都越界时
      报告来源序号（注释 release_notes.py:490 明示；公开约定
      README.md:246-248）。消息中的序号为去前导零后的形式
      （validate_change_index :279；公开约定 README.md:239-240）。

  第 4 步 写入
    重排与 UPDATE（release_notes.py:506-519）在全部检查通过之后
    才执行，且在 with conn 事务内（:489）；上述任一失败返回点都
    在写入语句之前，事务内没有任何已执行的修改，失败不会改动
    草稿。

失败结果的共同形态（公开约定 README.md:249-250）：
  - 退出码均为 1：fail 写标准错误并返回 1（release_notes.py:47-50），
    main 的返回值即进程退出码（release_notes.py:743-745、748-749）。
  - 标准输出均为空：失败路径不执行任何 stdout 写操作（成功输出
    在 release_notes.py:523，位于全部失败返回点之后）。
  - 标准错误只含相应消息和末尾一个换行：fail 用
    print(..., file=sys.stderr) 输出单行，print 自带一个末尾
    换行，无其他内容（release_notes.py:47-50）。
  - 不创建数据库、不补建表、不改变已有内容：第 1 步失败时未
    connect；第 2 步失败时只做了 SELECT（open_draft_for_update
    不执行任何建表语句，注释 release_notes.py:295-298）；第 3 步

五、不变性的源码依据（原文、标题、其他版本）
--------------------------------------------------------------------------------

以下三点中，“不变”的效果是公开约定（README.md:235-237），括号内
为对应的源码依据（源码推演）：

1. 每条变更的原文不变。move-change 的 UPDATE 只改 position 一列，
   且按 id 逐行定位（UPDATE changes SET position = ? WHERE id =
   ?，release_notes.py:516-519），没有任何语句改写 content；
   两行文本的内部换行、两条 新增预览 的文本均原样保留。

2. 标题与版本名不变。cmd_move_change 全函数只访问 changes 表，
   没有任何针对 drafts 表的 UPDATE/DELETE
   （release_notes.py:475-524）；标题只在 set-title 中被改写
   （release_notes.py:231-262）。因此 2.3 中 Title 行仍为 预览版。

3. 重复记录与其他版本不变。重排操作的对象是按 id 取出的该版本
   全部记录（SELECT id ... WHERE version = ? ORDER BY position，
   release_notes.py:506-513），两条 新增预览 作为两条独立记录
   分别参与排序、分别保留，不去重、不合并；UPDATE 的 WHERE 按
   id 限定单行，id 又来自该版本的查询结果，其他版本的记录不被
   读取也不被改写。条目数量不变：pop 之后 insert 同一元素，列表
   长度不变（:514-515）。
