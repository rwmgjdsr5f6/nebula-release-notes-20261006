  (10) print(f"Removed change: {args.version} #{index_text}")

为什么只删掉第二条“新增预览”，第一条同名记录保留：
  - 定位按“展示顺序中的第 N 条记录”进行，与内容无关：OFFSET 1 取的是

五、序号机制：展示序号、存储位置、多行文本与跨进程
--------------------------------------------------------------------------------

5.1 展示序号与存储位置的关系

  - 存储位置 position：changes.position 列，创建时由 enumerate 从 0
    起赋值（release_notes.py:86），一经写入不再被任何命令改写；
    remove-change 只删除目标行、不重排剩余行（release_notes.py:408-415），
    set-change 的 UPDATE 不带 position 赋值（release_notes.py:372-376）。
  - 展示序号：从 1 开始的“当前展示顺序中的第 N 条”。读取一律
    ORDER BY position（show 用 release_notes.py:119-126；定位用
    release_notes.py:335-339），序号 N 被翻译成 OFFSET N-1
    （release_notes.py:338），即“排序后跳过前 N-1 行取一行”。
  - 因此删除后序号按剩余记录重新计算，是“读时重算”，不是“写时
    重编号”：本例删除 position=1 后，原 position=2 的“改善提示”
    自动成为展示第 2 条；随后 set-change --index 2 命中的正是它。
  - 【公开约定】README.md:185-186：“删除后序号按剩余记录重新计算：
    set-change 按新序号定位，add-change 仍追加到末尾。”
  - 【源码推演】追加位置取 COALESCE(MAX(position), -1) + 1
    （release_notes.py:256-266）。本例删除后最大 position 仍为 2，
    下一次 add-change 会写入 position=3（展示上仍是第 3 条之前的
    末尾位置：当前两条之后），position=1 的空位保留。展示序号连续
    与存储 position 可以不连续，两件事互不矛盾。

5.2 多行文本为何只占一个序号

  - 每条 --change 插入 changes 的一行，文本（含内部换行）整体存于
    一个 TEXT 列 content（release_notes.py:81-88）；换行是列值内部
    的字符，不产生额外记录。
  - locate_change 的计数是 SELECT COUNT(*)（release_notes.py:320-323），
    定位是 LIMIT 1 OFFSET N-1（release_notes.py:335-339），二者都按
    行计数，与 content 里有多少换行无关。
  - 展示时每条记录只在整段文本前加一次 "- "，内部换行原样保留
    （release_notes.py:139-141；read_draft 注释 103-105）。
  - 【公开约定】README.md:51（show）、README.md:155-157（set-change）、
    README.md:182-184（remove-change）：序号“按记录而非输出行数计数，
    多行条目只占一个序号”。

5.3 新进程读取同一数据库为何仍保持顺序

  - 程序没有任何跨调用的内存状态：每次命令执行都新建 sqlite3 连接、
    用完在 finally 中关闭（remove-change 的连接开/关于
    release_notes.py:301、416-417；set-change 同构于 359-378；
    read_draft 开/关于 110、127-128）。
  - 删除与替换在 with conn 事务内执行，随 with 块正常退出提交
    （release_notes.py:396、363）；提交后状态只存在于 notes.sqlite
    文件。新进程用同一 --db 路径连接同一文件（README.md:14-16），
    read_draft 仍按 ORDER BY position 读回（release_notes.py:119-126），
    得到与上一进程结束时完全相同的条目与顺序。
  - 【公开约定】README.md:14-16（之后的进程使用同一路径即可继续读取
    与追加）、README.md:220（可在结束当前进程后于新进程用同一数据库
    路径查看）。

六、同一流程的失败优先级
--------------------------------------------------------------------------------

remove-change / set-change 的检查严格按“参数检查 → 定位版本 →
定位条目 →（仅 remove-change）最后一条保护 → 写入”的顺序短路，
前一阶段失败就不会进入后一阶段：

  阶段 0 参数检查：失败消息 Invalid draft
    remove-change：release_notes.py:388-390
    set-change   ：release_notes.py:348-356
    序号规则在 validate_change_index：release_notes.py:274-288
  阶段 1 定位版本：失败消息 Version not found: <版本名>
    open_draft_for_update：release_notes.py:298-299（文件不存在）、
    304-309（版本行不存在）
  阶段 2 定位条目：失败消息 Change not found: <版本名> #<序号>
    remove-change：release_notes.py:397-401
    set-change   ：release_notes.py:364-368
  阶段 3 最后一条保护（仅 remove-change）：
    失败消息 Cannot remove last change: <版本名>
    release_notes.py:405-406
  写入只可能发生在全部检查之后：
    UPDATE release_notes.py:372-376；DELETE release_notes.py:412-415

6.1 序号为 0：即使数据库不存在，也先报 Invalid draft

  例（静态推演，未实测）：
    python release_notes.py --db not-yet.sqlite remove-change demo-0.1 --index 0
  - 序号正则为 0*[1-9][0-9]*（release_notes.py:286），"0" 中没有
    非零数字，不匹配 → validate_change_index 返回 None
    （release_notes.py:286-288）。
  - cmd_remove_change 在 release_notes.py:389 即 fail("Invalid draft")，
    发生在 open_draft_for_update（:392）之前，因此根本不会执行
    os.path.exists 或 sqlite3.connect——数据库文件存不存在都不影响
    结果，也不会新建文件。
  - set-change 同理（release_notes.py:349-356 先于 :359）；此外
    --index/--change 缺失或重复、版本名或新文本空白也在同一阶段报
    Invalid draft。
  - 【公开约定】README.md:189-191（remove-change）、
    README.md:163-165（set-change）：即使目标版本不存在也优先返回
    Invalid draft。

6.2 序号合法，但数据库或版本不存在：Version not found: <版本名>

  - 数据库文件不存在：open_draft_for_update 先 os.path.exists
    （release_notes.py:298），不存在即 fail（:299）并返回，发生在
    sqlite3.connect（:301）之前——不会创建空文件。
  - 文件存在但 drafts 表中没有该版本行：SELECT 1 FROM drafts
    取空（release_notes.py:304-307），在 :309 fail 返回；此后不会
    去查 changes，更不会写入。
  - 两种情况的消息相同：Version not found: <版本名>。
  - 【公开约定】README.md:192-193、README.md:166-167。

6.3 版本存在但序号越界：Change not found: <版本名> #<序号>

  - locate_change 先 COUNT(*) 得当前条目数，再按十进制位数、同位时
    按字符串字典序比较 index_text 与 count_text
    （release_notes.py:320-333；大序号不转 int 是有意为之，注释见
    :281-283、:317-319）。越界时返回 (count, None)，调用方报
    Change not found（remove-change :398-401；set-change :365-368）。
  - 消息中的序号是去前导零后的 index_text。
  - 【公开约定】README.md:194-195、README.md:168-169。

6.4 只剩一条记录时：序号 2 报越界，序号 1 才报 Cannot remove last

  假设把本例草稿再删到只剩一条（仅用于说明优先级的静态推演状态），
  COUNT(*) = 1，count_text = "1"：
  - 请求 --index 2：位数相同，"2" <= "1" 不成立，locate_change
    直接返回 None（release_notes.py:325-333），走 6.3 的分支，
    报 "Change not found: demo-0.1 #2"。越界检查在最后一条保护

  - 请求 --index 1："1" <= "1"，定位成功并返回那条记录的
