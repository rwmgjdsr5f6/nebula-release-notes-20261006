四、主样例：list-drafts --prefix v1（静态推演预期）
--------------------------------------------------------------------------------

命令：

  python release_notes.py --db notes.sqlite list-drafts --prefix v1

沿第二节路径逐步推演：
  A. args.prefix == ["v1"]：非 None（154 行）、长度为 1、
     is_blank("v1") 为假（42-44 行）→ 校验通过，prefix="v1"（157 行）。
  B. notes.sqlite 存在 → 连接（163-164 行）。
  C. sqlite_master 中存在 drafts 表（168-172 行）→ 取数。
  D. SELECT version, title 取回四行（173-175 行），返回顺序取决于
     SQLite 物理存储，契约不依赖它，因为步骤 F 会重排。
  E. 按“版本名原文”做 str.startswith("v1")（181-183 行）：
       "v10"  : v,1 与前缀 v,1 相同，后续还有 '0'        → 命中
       "other": 首字符 'o' ≠ 'v'                          → 不命中
       "V1"   : 首字符 'V'(U+0056) ≠ 'v'(U+0076)         → 不命中
       "v1"   : 与前缀完全相同                            → 命中
     关键：匹配只看 row[0]（版本名）。other 的标题恰好是 "v1"，
     但标题从不参与比较（181-183 行只取 row[0]；README.md:82-84）；
     V1 因区分大小写被排除（README.md:85-86）。
  F. 对命中两行按版本名原文排序（187 行）："v1" 与 "v10" 前两个码点
     'v'(U+0076)、'1'(U+0031) 相同，"v1" 是 "v10" 的前缀且更短，
     Python 字符串比较中较短者在前 → v1、v10。
  G. 组装为两个只含 version/title 的对象（188-191 行），
     json.dumps(..., ensure_ascii=False) 输出，中文不转 ASCII（197 行）。

静态推演预期（逐字节）：
  退出码：0（198 行 → main 返回 → release_notes.py:724 退出）
  标准错误：空（成功路径不写 stderr）
  标准输出：恰为下面一行 JSON 数组，末尾恰有一个换行（197 行）：

[{"version": "v1", "title": "预览"}, {"version": "v10", "title": "后续"}]
  └─ 末尾一个换行（\n）

核对要点：
  - 输出顺序 v1 → v10 与创建顺序（v10 在第 1 位、v1 在第 4 位）相反，
    证明不按创建顺序；排序键只有版本名字符串（187 行）。
  - 不按语义版本大小：这里不存在任何版本号数值解析；规则是版本名原文
    的 Unicode 码点逐字符比较（README.md:68-69、85-87）。本样例中
    v1 先于 v10 只是“短前缀在前”的码点序结果，与数值 1 < 10 无关。
    规则层面的反例可由源码直接推定：码点序下 '1'(U+0031) < '2'
    (U+0032)，故 "v10" 会排在 "v2" 之前，而语义版本序恰好相反。
  - 每条草稿那条“示例”变更不出现在输出中：SELECT 不取 changes
    （173-175 行），每个元素只有 version、title 两个字段
    （README.md:63-64）。

六、逐字符匹配、通配符与 JSON 原文一致性（源码依据）
--------------------------------------------------------------------------------

1. 区分大小写、不裁剪、不解析语义版本
   筛选就是 Python 的 str.startswith（release_notes.py:182），前缀
   原文在 157 行取得后不经 strip/lower/任何转换；SQL 语句本身没有
   WHERE（173-175 行）。约定：README.md:85-87。样例中 V1 被排除即
   此规则；标题 "v1" 的 other 不参与即“只匹配版本名”规则。

2. 百分号 % 与下划线 _ 是普通字符
   因为根本没有使用 SQL LIKE（173-175 行是无 WHERE 的 SELECT，
   181-183 行在 Python 侧匹配），'%'(U+0025) 与 '_'(U+005F) 只匹配
   各自的字面字符，没有“任意串/任意单字符”通配含义
   （README.md:86-87；help 文本 release_notes.py:595-596）。
   静态推演示例（非固定样例数据，仅用于核对规则）：库存版本名为
   v%1、v_1、vA1 时，--prefix "v%" 只返回 v%1；--prefix "v_" 只
   返回 v_1；vA1 均不命中。

3. 前缀中的首尾空格与内部换行按原文比较
   前缀值原样进入 startswith（157、182 行），没有任何空白处理；
   is_blank（42-44 行）只拒绝“整个值为空或全部是空白”的前缀，
   不拒绝含空格/换行的非空白前缀：
     - " v1"、"v1 " 这类首尾带空格的前缀，空格(U+0020)作为真实
       码点参与逐字符比较，不会被裁掉；
     - 前缀含内部换行（如 "a\nb"，U+000A）时同样逐字符匹配，
       只命中版本名同位置含真实换行的草稿，不命中 "ab"。
   约定：README.md:85-86。
   注意边界："   "、" \t\n " 这种“整体仅含空白”的值仍属非法
   （44 行 str.isspace() 为真），走第七节的失败分支；合法与非法的
   分界就是 155 行的 is_blank，而不是“是否包含空白字符”。

4. 返回值经 JSON 往返后与保存原文一致
   items 的字符串直接取自 SELECT 结果（188-191 行），
   json.dumps(ensure_ascii=False)（197 行）：中文（如“预览”“后续”）
   直接输出，引号、反斜杠与控制字符（含真实换行）按 JSON 规则转义；
   用任意 JSON 解析器读回后，version 与 title 与数据库保存原文逐字符
   相等，首尾空格与内部换行均不丢失（README.md:65-67、85-86）。
   本样例四个标题无需转义，输出中即为中文原字。

七、失败优先级：非法 --prefix 先于一切数据库访问
--------------------------------------------------------------------------------

命令（注意 --prefix 位于末尾且不带值）：

  python release_notes.py --db missing.sqlite list-drafts --prefix

静态推演：
  1. argparse 见 --prefix 后无参数，按 nargs="?" + const=""
     （release_notes.py:592-593）把空串收入列表：
     args.prefix == [""]（不是 None）。
  2. 分发进入 cmd_list_drafts（598、720 行）。
  3. 154 行 prefixes is not None 为真；155 行 len==1 但
     is_blank("") 依 44 行 text=="" 为真 → 156 行
     return fail("Invalid draft")。
  4. fail（47-50 行）：49 行 print("Invalid draft", file=sys.stderr)
     由 print 补上末尾换行；50 行返回 1，经 release_notes.py:720、
     724 成为进程退出码。
  5. 此路径上没有任何 stdout 写入，197 行不可达 → 标准输出为空。
  6. 数据库访问全部在校验之后：os.path.exists 在 163 行、
     sqlite3.connect 在 164 行，均不可达 → missing.sqlite 不会被
     创建，目录下也不产生任何其他文件。

静态推演预期（逐字节）：
  退出码：1
  标准输出：空
  标准错误：恰为

Invalid draft
  └─ 末尾一个换行（\n），除此之外无任何内容

  文件系统：missing.sqlite 不被创建。

同样得到这一结果（退出码 1、stdout 空、stderr 恰为
"Invalid draft\n"、不建库）的非法取值（155 行逐一覆盖）：
  - 空值（显式缺值）：--prefix                 （const=""，593 行）
  - 显式空字符串：    --prefix ""              （is_blank 44 行 == 分支）
  - 仅含空白的值：    --prefix "   "、--prefix " \t\n "
                       （44 行 str.isspace() 分支，制表/换行也算空白）
  - 重复提供前缀：    --prefix v1 --prefix v1
                       --prefix v1 --prefix v2
                       （action="append" 使 len(prefixes)==2，
                        155 行 len != 1 即拒，与两个值是否合法无关）
优先级结论：参数校验先于文件存在性检查（源码注释 149-152 行明示；
README.md:90-92）。因此“数据库不存在 + 非法前缀”报 Invalid draft，
而“数据库不存在 + 合法前缀”输出 []（见第八节）——两条路径的分叉点
就是 156 行的提前返回与 163 行的存在性检查的先后关系。
即使数据库已存在且有数据，非法调用同样失败且不改动任何数据（本路径
无任何写语句）。

九、只读性与跨进程结果稳定
--------------------------------------------------------------------------------

1. 不补建表、不改草稿或变更（源码依据）
   cmd_list_drafts 函数体（release_notes.py:148-198）中只有两条
   只读语句：sqlite_master 上的 SELECT（168-171 行）与 drafts 上的
   SELECT（173-175 行）；没有 CREATE/INSERT/UPDATE/DELETE，没有
   executescript(SCHEMA)，也没有 with conn 事务或 commit。文件不
   存在时连 sqlite3.connect 都不发生（163 行门控 164 行）。
   约定：README.md:70-74、88-89（不创建数据库、不补建表、查询不
   改变任何草稿与变更的原文、数量或展示顺序，不创建其他文件）。

2. 数据未变化时，新进程查询结果相同
   每次进程都从 main 重新解析参数、重新连接（release_notes.py:714-720），
   输出只由 drafts 表当前行内容决定：筛选（182 行）与排序（187 行）
   都是确定性的纯函数。注意 173-175 行的 SELECT 本身没有 ORDER BY，
   物理返回顺序不具契约意义；187 行的 Python 排序使最终数组对同一数据
   恒定（按版本名码点确定全序），因此不同进程、重复执行得到逐字节相同
   的 stdout（README.md:72-74：“另一个进程使用同一路径查询得到相同
   数组”）。

本说明第八节目录化地穷尽了 README 承诺输出 "[]\n" 的四种情形；除此之外
不对结果做推定。下列情形 README 与 help 均未约定，静态核对时不得比照
