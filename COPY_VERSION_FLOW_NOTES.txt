二、核心操作：copy-version v1 --to v2
--------------------------------------------------------------------------------

命令（公开用法见 README.md:292-294）：

  python release_notes.py --db notes.sqlite copy-version v1 --to v2

按源码静态推演（cmd_copy_version，release_notes.py:664-734）：

  (1) 输入检查（release_notes.py:669-677）：to_names = args.to 得
      ["v2"]（:669）；is_blank("v1") 为假（:671，is_blank 定义
      :44-46）；to_names 非 None（:672）、长度恰为 1（:673）、
      is_blank("v2") 为假（:674），通过；new_version = "v2"
      （:677）。本步位于任何数据库访问之前（下一步在 :684）。
  (2) 打开并确认原草稿（release_notes.py:684-686，调用
      open_draft_for_update，:372-394）：notes.sqlite 已存在
      （os.path.exists 通过，:112-113）；drafts 表存在
      （sqlite_master 查询通过，:119-125）；SELECT 1 FROM drafts
      WHERE version = 'v1' 取到行（:388-390），返回连接。
  (3) 同一事务内按当前展示顺序读取原稿（with conn，:689；
      read_draft_on_conn，:694 调用、定义 :129-152）：标题取自
      drafts.title（:138-143）得“预览”；变更经
      SELECT content FROM changes WHERE version = ? ORDER BY
      position（:144-151）取回，按 position 升序在现存行
      {0, 2, 3} 上得到列表 ["甲", "重复", "重复"]——已删除的
      “临时”不在结果中，position 空洞不影响顺序。
  (4) 检查新名称占用（release_notes.py:704-708）：
      SELECT 1 FROM drafts WHERE version = 'v2' 无行（:704-706），
      conflict is None，继续。
  (5) 插入副本（release_notes.py:715-726，与上面的读取同在 :689
      的事务内）：先 INSERT drafts（"v2", "预览"）（:715-718），
      再 executemany 插入三条 changes，position 由 enumerate 从
      0 重新连续编号（:719-726）：
        ("v2", 0, "甲")
        ("v2", 1, "重复")
        ("v2", 2, "重复")
      事务随 with 块正常结束提交。原草稿 v1 的行在此过程中只被
      SELECT，没有任何语句以 v1 为目标做写入。
  (6) 输出并返回（release_notes.py:733-734）。

--------------------------------------------------------------------------------
四、复制语义：展示顺序、重复 / 多行 / 中文 / 空格、两份草稿互不影响
--------------------------------------------------------------------------------

4.1 当前展示顺序决定复制结果

复制读取与插入共用同一套顺序依据：
  - 读取经 read_draft_on_conn 的 SELECT content ... ORDER BY
    position（release_notes.py:144-151），复制在 cmd_copy_version
    内直接调用它（:694）。因此复制以“执行复制那一刻”原稿的现存
    记录与 position 升序为准：已删除的记录不出现（本例“临时”），
    经 move-change 调整过的顺序按调整后的顺序复制。这是公开约定
    （README.md:296-298）。
  - 插入时 position 由 enumerate(changes) 从 0 重新连续编号
    （release_notes.py:722-725），不沿用原稿的 position 值。
    本例原稿现存 position 为 0、2、3（remove-change 不重排，
    release_notes.py:539-542，源码推演），副本的 position 仍为
    连续的 0、1、2。position 空洞不被复制是公开约定
    （README.md:299-301）。
  - 读取与写入在同一事务（with conn，release_notes.py:689）内
    完成，列表 ["甲", "重复", "重复"] 既是读取顺序也就是插入
    顺序，中间没有第二次查询，故副本顺序与读取结果必然同序
    （源码推演）。

4.2 重复记录分别保留

“重复”“重复”在原稿中就是两行 changes（create 的 executemany
不去重，release_notes.py:85-92）；复制时 read_draft_on_conn
逐行取回两行（:144-151），cmd_copy_version 再 executemany 逐行
插入两行新记录（:719-726），全程没有 DISTINCT、去重或合并。
副本中它们仍是 position 1、2 两条独立记录，占两个展示序号。
公开约定见 README.md:299-300（“重复文本分别保留”）。

4.3 多行条目仍是一条记录（本例样例未出现，但规则相同）

内容里带内部换行的变更在库中始终只是一个 content、一行 changes：
create / add-change 不拆分（公开约定 README.md:28-29、192-194），
read_draft_on_conn 按行取回该字符串（release_notes.py:144-151，
docstring :129-137 明示“多行变更仍是一条记录”），复制按同一
字符串插入一行（:719-726），不复制出额外记录、不补齐或删除内部
换行；副本 position 仍一个序号。show 展示时只在首行前加 "- "，
内部换行原样保留（cmd_show，release_notes.py:179-182；公开约定
README.md:53）。因此“条目数量”按记录计，不按输出行数计。

4.4 中文、标点与首尾空格原样保留

整条复制链路（:694 读取 → :699 解构 → :715-726 插入）对 title
与每条 content 只做绑定传参，没有 strip、大小写转换或转义；
is_blank（release_notes.py:44-46）只用于入口校验，不修改文本。
SQLite TEXT 列按 Python 字符串原文存储（SCHEMA :29-41，源码
推演），标准输出在 main 中固定为 UTF-8（release_notes.py:935，
源码推演），故“预览”“甲”“重复”等中文逐字保留。同理，若标题
或某条变更含首尾空格（如 "  重复  "，整体非空白即通过校验），
空格随原文复制到副本并在 show 中出现在 "- " 前缀之后
（release_notes.py:180-182）。版本名同理：新名称按 args.to
原文保存，不裁剪空白、不转义（:677、:715-718；公开约定
README.md:302-303）。

4.5 修改原稿与副本互不影响的原因

两份草稿在存储层就是互不相连的两组行：
  - drafts 表以 version 为主键（SCHEMA，release_notes.py:30-33），
    v1 与 v2 是两行；复制只对 v2 执行 INSERT（:715-718），没有
    任何 UPDATE / DELETE 以 v1 为目标，v1 的标题不变。
  - changes 表每行带 version 列（SCHEMA，:34-40）。副本的三条
    变更是带新 version 值插入的全新行（:719-726），与原稿的行
    没有共享 id 或外键联动；原三行（position 0、2、3）原样保留。
  - 后续各修改命令都按 version 限定作用域：set-title 的
    UPDATE drafts ... WHERE version = ?（:342-345）、
    set-change 的 UPDATE changes ... WHERE version = ? AND
    position = ?（:503-507）、add-change 的 INSERT 携带该版本
    名（:432-436）、remove-change 的 DELETE 带 version 条件
    （:543-546）。对任一份操作的语句不会匹配另一份的行；两份的
    position 序列也各自独立（副本从 0 连续编号），在副本上
    set-change / remove-change 不影响原稿序号。
  这是公开约定（README.md:304-307；离线示例 README.md:533-538）。
  反向同理：复制完成后再修改原稿（增删改条目、set-title），新
  变化不会同步到副本——复制是一次性的内容拷贝，不是视图或链接
  （源码中两版本间不存在任何连接对象，源码推演）。

五、失败次序：输入检查 → 原稿查找 → 名称冲突检查
--------------------------------------------------------------------------------

cmd_copy_version 按下列先后返回失败，先命中先报
（release_notes.py:664-734）。三类失败全部经 fail 输出
（release_notes.py:49-52：print 到 stderr 并返回 1），故共同
形态为：退出码 1；标准输出空（0 字节，成功 print 在 :733，位于
所有失败返回点之后）；标准错误只含对应消息加一个换行（print
自带），无其他内容；返回值经 main（:939）与 sys.exit（:943）
成为进程退出码 1。

  第 1 步 输入检查（不触碰数据库）
    release_notes.py:669-676。以下情形一律 Invalid draft：
      - 原版本名为空或仅含空白：is_blank(args.version) 为真
        （:671；is_blank 定义 :44-46，空串或仅空白字符均算），
        如 copy-version "" --to v2、copy-version "   " --to v2。
      - 新名称为空或仅含空白：is_blank(to_names[0]) 为真
        （:674），如 --to ""、--to "   "。
      - 未提供 --to：该选项不设 default，省略时 args.to 为
        None（:672；参数定义 :920-927）。
      - 显式给出 --to 却缺值：--to 用 nargs='?' 配 const=""
        （:920-927），在命令末尾落空时收到空串，to_names 为
        ["""]，:674 的 is_blank 命中。
      - 重复提供 --to：action="append"（:922）收集成两个元素，
        len(to_names) != 1（:673），如 --to v2 --to v3。
    → 标准错误恰为：Invalid draft\n
    本步在 open_draft_for_update（:684）之前，即先于
    os.path.exists（:112）与 sqlite3.connect（:115）；即使
    notes.sqlite 不存在也先报本错误，本进程不打开、不创建
    数据库文件（公开约定 README.md:310-313）。

  第 2 步 查找原草稿（只读，不写入、不补建）
    open_draft_for_update，release_notes.py:372-394：
      - 数据库文件不存在：open_drafts_readonly 在 os.path.exists
        处直接返回 None（:112-113），不 connect、不建库
        （:383-384 转成失败）。
      - 文件存在但没有 drafts 表（完全空库或只有无关表）：
        sqlite_master 查询无行即关闭连接返回 None（:119-125），
        不补建 drafts / changes 表。
      - drafts 中查无原版本：SELECT 1 FROM drafts WHERE
        version = ? 无行（:388-390 → :391-393）。匹配按 SQL
        等值比较，SQLite 默认 BINARY 排序规则下逐字符精确匹配、
        区分大小写（源码推演）；仅大小写不同（如库中为 v1、命令
        给 V1）不匹配，属查无此版本。公开约定见
        README.md:314-316、302-303。
    → 标准错误恰为：Version not found: <原版本名>\n
      消息中的版本名原样取自命令行参数（fail 调用
      release_notes.py:384、393），即用户给的是 V1 就报
      “Version not found: V1”。公开约定 README.md:314-316。

  第 3 步 检查目标名称占用（原草稿确认之后）
    release_notes.py:704-708：SELECT 1 FROM drafts WHERE
    version = ? 以新名称精确查询（区分大小写，同上）。
      - 原草稿存在而新名称已被任一草稿占用：报
        Version already exists: <新版本名>（:707-708）。
      - 原名与新名完全相同（copy-version v1 --to v1）也属占用：
        查询命中的就是原草稿自己那一行，同样失败（:704-706；
        公开约定 README.md:317-318）。这一点与 rename-version
        不同，后者同名按成功处理（release_notes.py:634），复制
        流程没有同名豁免分支。
      - 原草稿不存在且目标名已占用时，仍报原稿不存在：冲突检查
        （:704）在原稿确认（:684）之后，流程在第 2 步已返回，
        根本不会执行占用查询（源码推演；与 README.md:314-318
        公布的先后一致）。
    → 标准错误恰为：Version already exists: <新版本名>\n
    另有并发兜底：INSERT 若撞上并发进程抢先创建的同名版本，
    sqlite3.IntegrityError 被捕获并报同一条消息
    （release_notes.py:727-729，源码推演，并发场景见第七节
    限制）。

失败时的不变性保证（公开约定 README.md:319-320）：
  - 不创建数据库：第 1 步失败时尚未 connect；第 2 步“文件不
    存在”在 os.path.exists 处返回（:112-113），全程不调用
    sqlite3.connect。
  - 不补建表：本流程任何分支都不执行 SCHEMA / CREATE TABLE；
    open_drafts_readonly 只查询 sqlite_master（:119-122），
    open_draft_for_update 与 cmd_copy_version 也没有建表语句
    （:372-394、:664-734）。
  - 不修改旧稿：失败返回点（:676、:384、:393、:698、:708）
    全部位于两条 INSERT（:715-726）之前；此前的语句只有
    SELECT。
  - 不留部分副本：drafts 行与 changes 行的插入同在 :689 的
    with conn 事务内且紧接执行（:715-726），冲突失败发生在
    插入之前；若插入中出现 IntegrityError 则事务回滚
    （:727-729）。任何失败后库中都不会出现“只有 drafts 行、
    没有条目”之类的半成品 v2。

1. 本说明全部命令结果均为按源码静态推演；按交付要求未执行
   release_notes.py，未运行 tests/ 或任何脚本，未创建
   notes.sqlite。第一、二、三、五节中的“预期结果 / 预期输出”
   不是实测输出。运行时的 Python 3 具体次版本、SQLite 版本与
   终端渲染效果不在静态核对范围内（README.md:3-4 声明仅依赖
   Python 3 标准库与内置 SQLite）。

2. 本说明只覆盖 copy-version 这一条流程及其失败优先级，以及为
   构造样例所必需的 create / remove-change / show 行为；不评价
   其他命令，也不替 README 补造未记载的约定（第六节已把纯源码
   推演的部分单独列出）。

3. 未约定的异常情形不推断为业务错误。例如：位置参数 version
   整体缺省、出现无法识别的选项等在 argparse 层面解析失败的

   README 公布的 Invalid draft 边界，本说明不把它们推演成业务
   结果；数据库文件损坏、磁盘只读等情形同样超范围。

4. 并发场景（两个进程同时复制到同一新名称）不在本说明实测范围

5. 样例覆盖的边界以 README.md:290-320 已公开者为限：正常本地

结论：以 notes.sqlite 中的固定草稿 v1（标题“预览”，初始四条
甲 / 临时 / 重复 / 重复，第二条“临时”已由 remove-change 删除，
复制时现存展示顺序为 甲、重复、重复，position 为 0、2、3）为
例，python release_notes.py --db notes.sqlite copy-version v1
--to v2 预期退出 0、标准错误为空（0 字节），标准输出恰为
“Copied version: v1 -> v2”加一个换行（冒号后、-> 两侧各一个
空格，无其他空格或空行）；随后 python release_notes.py ...
show v2 预期退出 0、标准错误为空，标准输出恰为五行 Version: v2、
Title: 预览、- 甲、- 重复、- 重复，每行一个换行、末尾恰一个
换行。副本显示新名称、原标题与复制时同序的三条现存变更；顺序由
ORDER BY position 的读取（release_notes.py:144-151）决定，已
删除条目不复制，副本 position 经 enumerate 重排为连续的 0、1、2
（:722-725）；重复文本是两行独立记录，多行文本始终一条记录，
中文、标点、首尾空格与内部换行在无裁剪、无转义的链路中原样保留；
两份草稿是按 version 区分的独立 drafts / changes 行，后续修改
互不影响。失败严格按 输入检查 → 原稿查找 → 名称冲突 的次序：
空白原名或新名、--to 未提供 / 缺值 / 重复提供报 Invalid draft；
输入有效但数据库不存在、无 drafts 表或原稿不存在（仅大小写不同
也算不存在）报 Version not found: <原版本名>；原稿存在而目标名
占用（含 v1 复制到 v1）报 Version already exists: <新版本名>；
原稿不存在且目标名占用时仍报原稿不存在。以上失败均退出 1、
标准输出为空、标准错误只含对应消息和一个换行，且不创建数据库、
不补建表、不修改旧稿、不留部分副本。全部结论可由 README.md
公开约定（290-320 等）与 release_notes.py 当前源码逐行推出，
公开约定与源码推演的区分见第六节，样例结果均为静态推演的预期
值而非实测。
